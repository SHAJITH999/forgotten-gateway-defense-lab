- avoiding duplicate events

PHASE 3 — NGINX LOG PARSER
--------------------------
Parse Nginx access-log entries into structured events.

Extract fields where available:

- timestamp
- source IP
- HTTP method
- requested path
- HTTP protocol
- status code
- response size
- referrer
- user agent
- host
- raw log line

Example raw event:

127.0.0.1 - - [16/Sep/2026:23:58:31 +0530]
"POST /login HTTP/1.1" 401 1234

Convert it into something similar to:

{
  "timestamp": "...",
  "source": "nginx",
  "event_type": "http_request",
  "source_ip": "127.0.0.1",
  "method": "POST",
  "path": "/login",
  "status": 401,
  "user_agent": "...",
  "raw_log": "..."
}

Keep raw evidence available.

Do not force MITRE mappings onto every normal event.

A raw HTTP request is an event.

PHASE 5 — SECURITY EVENT DETECTION
----------------------------------
Implement a simple transparent detection/correlation layer.

Do NOT claim that a single HTTP request proves a real attack.

Use rule-based detection appropriate for a controlled training environment.

Examples:

1. Repeated failed authentication requests
   - Multiple POST /login requests
   - HTTP 401/403 responses
   - Correlate within a configurable time window

2. Suspicious access to administrative paths
   - /admin
   - /administrator
   - /management
   - etc.

3. Suspicious web request patterns
   - unusual probing
   - repeated access to sensitive application paths
   - abnormal request frequency

4. Unusual outbound/transfer behavior if application logs provide evidence

Every detection must contain:
- timestamp
- severity
- reason
- related events
- source IP
- detection rule
- confidence
- MITRE technique if applicable

Avoid automatically labeling generic suspicious strings as successful exploitation.
